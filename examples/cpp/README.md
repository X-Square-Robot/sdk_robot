# C++ examples

Recorder-based collection and replay have dedicated examples under
[`data_collection_v2/`](data_collection_v2/README_CN.md). Build `data_collection_v2`
for start/stop/download and `data_replay_v2` for the converted protobuf recordings.

Every executable uses the public C++ `Robot`/service facade and generated
protobuf messages; no private transport or duplicate message type is used.
C++ has one current public API, so it has no `v1`/`v2` directory split.

The standalone CMake file at `examples/cpp/CMakeLists.txt` builds targets from
`examples.cmake`. Target names follow their relative source paths, for example
`camera` and `quanta_x2_waist_control`.

| Python v1 behavior (also implemented by Python v2) | C++ counterpart |
| --- | --- |
| `check_connect.py` | `check_connect.cpp` |
| `system.py`, `robot_status.py`, `robot_control.py` | `system.cpp`, `robot_status.cpp`, `robot_control.cpp` |
| `chassis_control.py`, `head_control.py` | `chassis_control.cpp`, `head_control.cpp` |
| `camera.py` | `camera.cpp` |
| `depth_points.py`, `imu.py`, `radar.py` | `depth_points.cpp`, `imu.cpp`, `radar.cpp` |
| `tof.py`, `ultrasonic.py`, `tf.py` | `tof.cpp`, `ultrasonic.cpp`, `tf.cpp` |
| `audio.py`, `navigation.py` | `audio.cpp`, `navigation.cpp` |
| `data_collection_example.py`, `data_replay_example.py` | `data_collection_example.cpp`, `data_replay_example.cpp` |
| `desktop/*.py` | matching `desktop/*.cpp` targets |
| `quanta_x1/*.py`, `quanta_x2/*.py` | matching `quanta_x1/*.cpp` / `quanta_x2/*.cpp` targets |

Most binaries accept a positional `host:port`; Quanta X3 waist and lidar examples
use `--server host:port`. The camera examples additionally accept the options
shown below. All request failures include the standardized
error name/message and request id in the terminal output.

每个公共 `.cpp` 都是一个独立、可复制的小程序。连接、请求、结果检查和关闭
都在同一个文件里；没有示例之间的共享控制器或场景调度代码，想改一个场景时
只需改对应的文件。

## Quanta X3 end-pose stream

`quanta_x3_arm_control <host:port> left stream end_pose` (or `right`)
first enters SDK work mode and `MANIPULATOR_END_POSE`, matching the Python
example. It then waits for pose feedback without sending pose targets.
Mode setup failure stops the request; normal exit and Ctrl+C use the existing
IDLE cleanup. Joint-state streaming does not change modes.

## Build and run

Use a matched Client, protocol and sdk_common checkout. For a published
simulator release, check out the workspace commit listed in its deployment
SOP before initializing the submodules. Do not update a single submodule to
a different release. The commands below run from the workspace root on
Ubuntu 24.04 x86_64 and build the C++ Client without ROS or a Python wheel.

```bash
sudo apt-get update
sudo apt-get install -y build-essential cmake git pkg-config python3-dev \
  libprotobuf-dev protobuf-compiler libgrpc++-dev protobuf-compiler-grpc
git submodule update --init --recursive client protocol sdk_common

export SDK2_CPP_ROOT="$PWD/.sdk-client-install"
cmake -S client/native -B build/client-native \
  -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX="$SDK2_CPP_ROOT" \
  -DSDK_BUILD_AS_COLCON=OFF -DSDK_BUILD_SHARED_CLIENT=ON \
  -DSDK_PROTO_ROOT="$PWD/protocol/proto" \
  -DSDK_COMMON_INCLUDE="$PWD/sdk_common/include" \
  -DPython3_EXECUTABLE=/usr/bin/python3
cmake --build build/client-native --parallel "${BUILD_JOBS:-4}"
cmake --install build/client-native

cmake -S examples/cpp -B build/examples \
  -DCMAKE_BUILD_TYPE=Release -DX2ROBOT_SDK_ROOT="$SDK2_CPP_ROOT" \
  -DX2ROBOT_PROTOBUF_LIBRARY="$(c++ -print-file-name=libprotobuf.so)" \
  -DX2ROBOT_GRPCPP_LIBRARY="$(c++ -print-file-name=libgrpc++.so)" \
  -DX2ROBOT_GRPC_LIBRARY="$(c++ -print-file-name=libgrpc.so)" \
  -DX2ROBOT_GPR_LIBRARY="$(c++ -print-file-name=libgpr.so)"
cmake --build build/examples --target check_connect tf --parallel "${BUILD_JOBS:-4}"
export LD_LIBRARY_PATH="$SDK2_CPP_ROOT/lib${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
ldd build/examples/tf
./build/examples/check_connect 127.0.0.1:55051
./build/examples/tf 127.0.0.1:55051 static
```

`SDK2_CPP_ROOT` must contain `include/` and `lib/`, rather than the source or
build directory. `ldd` must show no `not found` entries. The explicit protobuf
and gRPC paths above use the same system libraries used to compile the Client;
do not mix them with headers generated by a different protobuf version. For
an extracted SDK artifact that bundles these libraries in `lib/`, omit the
four library overrides and set `X2ROBOT_SDK_ROOT` to that artifact root.
Omit `--target check_connect tf` to build all available examples. Set
`BUILD_JOBS` to a suitable parallelism for the build host.

For a remote simulator listening only on loopback, keep an SSH tunnel open
in another terminal (replace the account, host and remote port as needed):

```bash
ssh -N -L 18552:127.0.0.1:55052 xr@SIMULATOR_HOST
./build/examples/check_connect 127.0.0.1:18552
./build/examples/tf 127.0.0.1:18552 static
```

Ping checks connectivity. TF needs an active data source. `static` prints
the first non-empty static message and cancels the subscription immediately;
it does not enumerate every possible publisher or wait for static data to
change. An empty message, missing data or an RPC error returns a nonzero exit
code. `stream` reads dynamic TF until Ctrl+C (exit 130) or a read failure.
`tree` combines one static snapshot with a three-second dynamic window and
returns nonzero if either subscription fails. A partial tree printed on
failure is not a successful result. Desktop scenes without static TF should
use `stream`; a static timeout is not evidence that dynamic TF is unavailable.

Body `stream` commands also return nonzero on a timeout, SDK error or RPC
disconnect, including failures after valid samples. Reading the waist end-pose
stream does not change work or manipulator mode. These commands are read-only;
movement requires an explicit `move` action.

The loopback regressions run the actual examples against fake TF and body
services, without a robot. They verify error propagation after valid data and
reject any mode write from a body stream command:

```bash
cmake -S examples/cpp -B build/examples -DSDK_EXAMPLES_BUILD_TESTS=ON
cmake --build build/examples --parallel "${BUILD_JOBS:-4}"
ctest --test-dir build/examples --output-on-failure
```

## Robot homing

`robot_control` waits up to 60 seconds for homing by default, allowing the
server's 30-second completion wait plus mode-switching and communication time.
It returns as soon as homing completes. Override only the homing RPC budget
with a positive integer number of seconds:

```bash
./build/examples/robot_control 127.0.0.1:55051 homing
./build/examples/robot_control 127.0.0.1:55051 homing --timeout 35
```

A timeout returns a nonzero exit code and does not confirm that robot motion
has stopped. Check the robot's state before sending another motion command.
`stop`, `recover` and work-mode requests keep their existing timeout budgets.

## Camera display

`camera` copies each callback view before doing any work. It supports the same
head/left-arm/right-arm/all actions as the Python examples. Use `--show` to
send a JPEG/PNG/H.26x packet to `ffplay`, or `--output`/`--save-dir` to keep
the encoded packet. Streams run until Ctrl+C unless `--seconds` is supplied:

```bash
./build/camera head rgb-image 127.0.0.1:55051 --show
./build/camera left_arm stream 127.0.0.1:55051 --seconds 5 \
  --output ./camera_output
./build/camera all 127.0.0.1:55051 --save-dir ./camera_output
```

Single-image previews stay open until you close the window or press Q/Esc.
With `all --show`, close each preview to continue to the next camera. Video
previews still close when the stream ends. A single-image display failure prints
the player error and returns a nonzero exit code; use `--no-show` for headless capture.

On Quanta X3, `all` captures a decoded PNG from each of the four public video
streams (both head eyes and both wrists); single-image actions also decode a
video frame because X3 does not expose single-image RPCs. These captures require
`ffmpeg` and fail if a stream cannot produce a decoded frame.

Install `ffmpeg` on the client host before running data collection; camera
streams are finalized as H.264 MP4 files when an episode stops. `ffplay` is
optional for live windows, and no OpenCV development headers are required to
compile the C++ examples.

## Data collection

`data_collection_example` follows the Python v1 collector flow: it selects a
model preset, opens the enabled streams concurrently, writes a manifest and
timestamped episode files, and can retain raw camera data. `data_replay_example`
replays a recorded episode in joint or end-pose mode. The lower-level
`data_collection` and `data_collection_data_collector` targets are useful for
small focused captures:

EX001 master-arm streams are optional: without a teleoperation master they may
remain silent. The C++ collector keeps waiting when the first frame times out,
so a master connected later can still be recorded. An episode with missing
master data prints one `WARNING` summary after recording stops and includes
per-stream warnings in `episode.json`; empty master streams stay quiet while
recording. The episode contains no fabricated
master samples. Transport and SDK errors remain errors. If no master data is
needed, pass `--no-master-arm-data` to either the C++ or Python v2 example.

The `x3` / `quanta_x3` preset records six joint groups, both arm end poses,
the waist end pose, four camera streams, odometry, chassis IMU and four
ultrasonic sensors. Pose feedback must already be publishing in the robot's
current mode; collection does not switch modes. Missing or failed enabled
pose streams make recording fail, with partial files and errors retained for
diagnosis. Quanta X3 end-pose replay requires all three recorded pose streams
and rejects incomplete episodes before switching modes or sending commands.

The Python v2 replay and C++ exit cleanup wait up to 35 seconds for IDLE.
Task shutdown and WBC stop run sequentially, and long Cartesian replays can
take more than 11 seconds to stop WBC. The matching server must also include
the extended WBC stop budget; updating only the example cannot extend its
internal timeout. Cleanup sends one request, reports rejection or timeout as
failure, and never retries motion or claims a timed-out transition succeeded.
The preset does not request the
withdrawn TOF or LaserScan interfaces. All three collector entries select this
preset automatically when the connected robot reports `quanta_x3`.
X3 replay tracks recorded odometry through the public velocity interface, with
the same 0.3 m/s and 0.5 rad/s limits as the Python example. Any failed motion
record stops replay and returns a nonzero exit status; sensor-only records are
not sent as commands.

```bash
./build/data_collection_example 127.0.0.1:55051 ./collected_data x2 \
  --seconds 5 --once
./build/data_replay_example ./collected_data/episode_000 127.0.0.1:55051 \
  --mode joint_pos --speed 1.0 --yes
```

Both `data_replay_example` and `data_replay` accept the same mode arguments.
The positional `end_pose` is a replay mode, not a replacement server address.
Named options also accept `--mode=end_pose` and can appear before or after the
episode directory. Unknown options, invalid modes and invalid numeric values
fail before connecting. `data_replay_example` asks for confirmation unless
`--yes` is supplied; `data_replay` retains its non-interactive behavior.

```bash
# Inspect the recorded streams without connecting or sending commands.
./build/data_replay_example ./collected_data/episode_000 127.0.0.1:55051 \
  end_pose --dry-run
# End-pose replay: positional and named forms are equivalent.
./build/data_replay_example ./collected_data/episode_000 127.0.0.1:55051 end_pose
./build/data_replay_example ./collected_data/episode_000 \
  --server 127.0.0.1:55051 --mode end_pose
./build/data_replay --help
```

End-pose replay consumes recorded arm and waist pose streams; it does not
compute Cartesian poses from joint-only recordings. Check the `--dry-run`
plan for the streams needed by the selected robot and control mode.

Quanta X3 end-pose replay refreshes the left arm, right arm and waist together
with a target rate of 50 Hz, sampling the same playback timestamp for all three. Position uses
linear interpolation and orientation uses shortest-path quaternion SLERP,
matching Python collection alignment. Gaps between recorded poses are
interpolated; outside a stream's time range its boundary pose is held. This
cannot reconstruct movements that were not recorded during a mode switch.
RPC time counts toward the control period; only the remaining time is spent
waiting. Successful calls taking longer than a period stretch the replay
duration without skipping ahead in the pose timeline or sending catch-up bursts.
There is no fixed 100 ms cycle cutoff. Each command RPC has a 300 ms timeout.
An end-pose RPC timeout prints a WARNING and continues with the remaining
targets and subsequent trajectory without resending that command. Its execution
is unconfirmed; the final `pose_timeouts` count reports these calls. Other
errors still stop replay. A wired connection helps the actual playback speed
stay close to the requested speed.
The `--dry-run` plan counts source records, not the resampled pose commands.

Use `--no-chassis` to omit all chassis mode and motion calls, even when the
episode includes odometry:

```bash
./build/data_replay_example ./collected_data/episode_000 \
  --server 127.0.0.1:55051 --mode end_pose --speed 1 --no-chassis
```

The Python v2 replay example can read this C++ protobuf episode directly;
no intermediate JSON conversion is required.

Without `--seconds`, enter a task name and press Enter again to start. Press
Enter during recording to stop, save the episode, and choose whether to record
another one. EOF also finishes the current episode; EOF at a start prompt
exits without starting a recording. Ctrl+C/SIGTERM drain the streams and save
the current episode before exiting with status 130. Collection only reads
robot streams and does not change the robot's work mode.

To run the terminal and pipe input regression without a robot:

```bash
cmake -S examples/cpp -B build/examples-cpp -DX2ROBOT_SDK_ROOT="$PWD/artifacts" \
  -DSDK_EXAMPLES_BUILD_TESTS=ON
cmake --build build/examples-cpp --target data_collection_example body_stream_test_server
ctest --test-dir build/examples-cpp -R '^collection_input_regression$' --output-on-failure
```

## quanta_x3

quanta_x3 目录包含 arm、waist、gripper、lidar_points 四个机型差异入口；头部、底盘、系统、
音频、导航和其他只读能力直接使用本目录根部的公共产物。完整入口和轨迹说明见
[quanta_x3 示例说明](../QUANTA_X3_README.md)。C++ 腰部入口为 `quanta_x3_waist_control`，
与 Python `waist_control.py` 使用相同参数和控制逻辑，默认只读，支持三关节和末端平滑相对运动。
C++ 雷达点云入口为 `quanta_x3_lidar_points`，支持与 Python 相同的 `--server`、
`--action single|stream|verify` 和 `--seconds`，运行命令见 [X3 C++ 说明](quanta_x3/README.md)。

Sensor stream commands return a nonzero exit status when opening, reading or
cancelling the stream fails. Head streams follow the same rule. For `tof
both-stream` and `ultrasonic all-stream`, a failed reader stops the group and
makes the command fail. Ctrl+C still exits with status 130.

`depth_points` validates the payload size and x/y/z field layout before printing
points. It respects row padding and byte order; malformed or empty payloads
return a nonzero status. The sensor regression also reads a cloud larger than
4 MiB through the ordinary `Robot::Create` path. Build with a matching current
Client: older bundles retain their original gRPC receive limit.
