# SDK Client 版本命名规则

本文说明 `x2robot` Python 客户端（`client/`，包名 `x2robot`）的版本号约定。版本号以 [`client/pyproject.toml`](../client/pyproject.toml) 中的 `version` 为准，Git tag 与其保持一致。

## 1. 基本格式

采用 **语义化版本（SemVer）三位主格式**：

```text
MAJOR.MINOR.PATCH
```

| 字段 | 含义 | 何时递增 |
|------|------|----------|
| `MAJOR` | 主版本 | 不兼容的 API / 行为变更 |
| `MINOR` | 次版本 | 向后兼容的功能新增 |
| `PATCH` | 修订号 | 向后兼容的问题修复 |

示例：`1.1.0`、`1.1.1`、`1.2.0`。

对应 Git tag 加 `v` 前缀：

```text
v1.1.0
v1.1.1
```

`pyproject.toml` 中**不写** `v` 前缀：

```toml
version = "1.1.1"
```

## 2. 日常发版（主线）

主线只使用三位版本，按变更类型抬号：

| 变更类型 | 示例 |
|----------|------|
| 不兼容变更 | `1.1.5` → `2.0.0` |
| 兼容的新功能 | `1.1.5` → `1.2.0`（PATCH 归零） |
| 兼容的修复 | `1.1.5` → `1.1.6` |

规则：

- 抬 `MAJOR` 时，`MINOR`、`PATCH` 归零。
- 抬 `MINOR` 时，`PATCH` 归零。
- 主线正常迭代**不要**使用第四位数字。

## 3. 预发布版本（可选）

需要提前给内部或灰度验证时，在三位版本后加预发布后缀（PEP 440 / SemVer 常见写法）：

```text
MAJOR.MINOR.PATCH-preN
```

示例：

```text
1.2.0-pre1
1.2.0-pre2
```

Tag：`v1.2.0-pre1`。

排序关系（示意）：

```text
1.2.0-pre1 < 1.2.0-pre2 < 1.2.0
```

正式版发布后，预发布号不再用于该正式版之后的修复；修复走 `PATCH` 或新的预发布线。

## 4. 热修复（Hotfix）

### 4.1 主线尚未越过当前修订号

若当前维护的就是最新主线修订（例如最新正式版仍是 `1.0.7`），hotfix **直接抬 PATCH**：

```text
1.0.7 → 1.0.8
```

这是默认、优先的方式，与常见开源项目一致。

### 4.2 需要并行维护旧的 minor / patch 线

主线已经前进（例如已发布 `1.1.0`），仍需给旧线用户打补丁时：

1. 从对应 tag（如 `v1.0.7`）拉出维护分支（建议命名：`release/1.0` 或 `hotfix/1.0.x`）。
2. 在该维护线上继续使用**三位**版本，从该线上**尚未占用**的下一个 `PATCH` 递增。
3. 同一修复尽量 cherry-pick 回主线；若主线已包含等价修复，主线不必仅为对齐而抬号。

示意：

```text
main:            1.0.7 ──► 1.1.0 ──► 1.1.1
                   │
release/1.0:       └──► 1.0.8 ──► 1.0.9
```

此时 `1.0.8` 是 **1.0 维护线** 的版本，与主线 `1.1.x` 并行，不会“覆盖”或破坏主线。

### 4.3 第四位数字（仅作例外）

仅当出现以下情况时，才允许使用第四位：

- 必须给某个**已发布**的精确版本（如 `1.0.7`）打补丁；且
- `1.0.8` 等后续三位号已被主线或其他发布占用，无法再按三位干净递增。

格式：

```text
MAJOR.MINOR.PATCH.HOTFIX
```

示例：`1.0.7.1`、`1.0.7.2`。

排序（PEP 440 合法）：

```text
1.0.7 < 1.0.7.1 < 1.0.7.2 < 1.0.8
```

约束：

- 第四位**只**表示维护线紧急热修，不用于新功能。
- 不要把第四位当作日常默认格式；新主线版本仍发三位（如 `1.1.0`，不要发成 `1.1.0.0` 除非团队另行统一）。
- Tag：`v1.0.7.1`；`pyproject.toml`：`version = "1.0.7.1"`。

> 历史 tag 中已存在 `v1.0.7.1`、`v1.0.7.2`、`v1.0.7.3` 等形式，视为该例外规则的存量用法；新发版优先走 §4.1 / §4.2。

## 5. 版本与发布物对齐

发版时以下内容必须一致：

| 位置 | 示例 |
|------|------|
| `client/pyproject.toml` → `version` | `1.1.1` |
| Git tag | `v1.1.1` |
| 构建产物名（wheel） | `x2robot-1.1.1-*.whl` |

建议流程：

1. 更新 `client/pyproject.toml` 中的 `version`。
2. 提交变更并打 tag：`git tag v1.1.1`。
3. 构建并发布对应 wheel。
4. 在 Release / Changelog 中简要说明变更类型（breaking / feature / fix）。

## 6. 依赖声明建议（给使用方）

使用方锁定兼容范围时，推荐按主版本约束，例如：

```text
x2robot>=1.1.0,<2
```

预发布版默认不应被 `>=1.2.0` 之类的稳定约束误选中（pip / PEP 440 对 pre-release 有单独规则）；生产环境如无必要，不要安装 `*-preN`。

## 7. 速查

| 场景 | 版本示例 |
|------|----------|
| 兼容修复（主线） | `1.1.0` → `1.1.1` |
| 兼容新功能 | `1.1.1` → `1.2.0` |
| 不兼容变更 | `1.2.0` → `2.0.0` |
| 预发布 | `1.2.0-pre1` |
| 旧 minor 维护线修复 | 主线已到 `1.1.x` 时，维护线发 `1.0.8` |
| 三位号已被占用的精确热修（例外） | `1.0.7.1` |

## 8. 不采用的方案

以下方案**不作为**本 SDK Client 的版本主规则：

- **日历版本**（如 `年.月.周` / `2026.7.4`）：便于看出发布时间，但不表达 API 兼容性，也不利于 pip 依赖范围声明。若需标识构建时间，可放在制品文件名、镜像 tag 或 Release 说明中，而不写入包版本号主格式。
- **主线日常固定四位**（如始终 `1.1.0.0`）：偏离常见开源 SemVer 习惯，增加沟通成本；第四位仅保留给 §4.3 例外。
